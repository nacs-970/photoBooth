**Type:** SYNTHETIC (generated by ffmpeg, not downloaded from freesound.org)

**Command used:**
```bash
ffmpeg -f lavfi -i "anoisesrc=c=pink:r=44100:d=0.08" \
  -af "volume=0.7,highpass=f=800,lowpass=f=8000,afade=t=in:st=0:d=0.005,afade=t=out:st=0.05:d=0.03" \
```

## Countdown Loop Implementation

**Choice: `setInterval(50ms)` — NOT `requestAnimationFrame`**

**Rationale:** The SVG ring animation is driven entirely by CSS `transition: stroke-dashoffset {countdownMs}ms linear` — the DOM only needs the initial `elapsed` update to kick off the CSS transition. The loop's only job is:
1. Track elapsed time accurately to compute the `digit` (3→2→1)
2. Detect the terminal condition (`elapsed >= COUNTDOWN_MS`) and trigger capture

A 50ms interval is precise enough for both without the overhead of rAF on every frame. rAF would run 60x/second updating a CSS-driven animation that doesn't need 60fps input. The `setInterval` approach is simpler, easier to clean up, and produces identical visual output.

The digit updates discretely at 1000ms boundaries via `$derived(Math.max(1, Math.ceil((COUNTDOWN_MS - elapsed) / 1000)))`.

## Decisions Made

1. **Countdown loop: setInterval(50ms)** — CSS handles smooth animation; interval only needed for digit steps and terminal detection. rAF would over-sample for CSS-driven animation.

2. **Shutter asset: ffmpeg synthetic** — ffmpeg available on host (Linux), produces a real MP3 binary rather than a PLACEHOLDER stub. Avoids a blocking note in summary.

3. **FlashOverlay CSS test strategy: source-level assertions** — happy-dom cannot resolve CSS custom properties (`var(--motion-flash)`) in `getComputedStyle`. Source-level `readFileSync` + string checks are reliable and explicit.

4. **Audio mock constructor pattern: function keyword** — `vi.fn().mockImplementation(() => instance)` with arrow function fails as constructor. Regular function syntax required: `vi.fn().mockImplementation(function() { return instance; })`.

5. **CountdownScreen always mounts FlashOverlay** — `<FlashOverlay visible={flashVisible} />` always rendered (not behind `{#if}`) so CSS fade-out transition fires when `visible` switches false after the flash.
