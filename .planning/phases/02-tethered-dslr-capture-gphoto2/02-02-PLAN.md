## Phase Goal

**As a** kiosk host, **I want to** choose between Tethered DSLR and Webcam on every boot, **so that** the app always starts in a known camera state and I can use the real DSLR when it is connected.

<objective>
FPS spike + stream strategy decision. This plan does no coding. It exists to resolve the single highest-risk empirical gap in Phase 2 before Wave 3 writes the MJPEG stream handler.

Purpose: RESEARCH.md flags that gphoto2 --capture-movie FPS varies per camera body (2–17 fps). The Wave 3 CameraService implementation forks on this result: --capture-movie (push-based SOI/EOI scanning) vs --capture-preview poll loop (simpler, more predictable ~5-10 fps). Running Wave 3 without this data risks implementing the wrong strategy.
Output: A recorded decision (stream strategy) and measured FPS/lag values that the Wave 3 executor uses directly.
</objective>

  <name>Task 1: DSLR FPS spike — measure capture-movie throughput</name>
  <what-built>Nothing yet. This task collects empirical data before Wave 3 writes the stream handler.</what-built>
  <how-to-verify>
    PREREQUISITE: Connect your DSLR camera to this machine via USB. If gvfs claims the device, quit Image Capture / Shotwell / gvfs first (see gphoto2 -53 notes in RESEARCH.md).

    Run the following measurement commands (each ~10 seconds):

    **Step 1: Verify camera is detected**
    ```bash
    gphoto2 --auto-detect
    ```
    Expected: Your camera model appears in the list.

    **Step 2: Measure capture-movie FPS**
    ```bash
    # Count JPEG frames per second for 10 seconds
    gphoto2 --capture-movie --stdout 2>/dev/null | \
      python3 -c "
    import sys, time
    data = b''
    frames = 0
    start = time.time()
    while (elapsed := time.time() - start) < 10:
        chunk = sys.stdin.buffer.read(65536)
        if not chunk: break
        data += chunk
        count = data.count(b'\xff\xd9')
        if count > frames:
            frames = count
    print(f'{frames} frames in {elapsed:.1f}s = {frames/elapsed:.1f} fps')
    "
    ```

    **Step 3: Measure perceived lag** (visual check)
    ```bash
    gphoto2 --capture-movie --stdout 2>/dev/null | ffplay -i - -f mjpeg 2>/dev/null
    ```
    Move your hand in front of the lens and estimate the delay between movement and display.

    **Record your results:**
    - Camera model: ________________
    - Measured FPS: ________________
    - Perceived lag: ________________ (e.g. "< 1s", "2-3s", "5s+")

    **Decision rule:**
    - FPS >= 5 AND lag < 2s → use **capture-movie** (SOI/EOI scanner in CameraService)
    - FPS < 5 OR lag >= 2s → use **capture-preview poll loop** (execFile loop every 150ms)
  </how-to-verify>
  <resume-signal>
    Type one of:
    - `movie fps={N} lag={description}` (e.g. "movie fps=12 lag=<1s")
    - `poll fps={N} lag={description}` (e.g. "poll fps=? lag=? — capture-movie showed 2fps")
    - `skip camera-not-available` if no DSLR is available — Wave 3 will implement capture-movie as the default with a TODO comment noting the fallback
  </resume-signal>

<task type="checkpoint:decision">
  <name>Task 2: Confirm stream strategy for Wave 3</name>
  <decision>Which gphoto2 live-view strategy should CameraService.startStreamProcess() use?</decision>
  <context>
    Wave 3 implements GET /api/camera/stream in server/src/camera/CameraService.ts. The two options have the same external interface (multipart/x-mixed-replace on the same endpoint) but different internal implementation.

    The FPS measurement from Task 1 drives this decision. Both options are fully described in RESEARCH.md Architecture Patterns (Pattern 1 + D-05 clarification).
  </context>
  <options>
    <option id="option-movie">
      <name>capture-movie (SOI/EOI scanner)</name>
      <pros>Push-based — no polling overhead. Camera sends frames at its native rate. Lower CPU than polling.</pros>
      <cons>Requires SOI/EOI byte scanning in a rolling buffer. FPS is camera-body-dependent. 2-5s lag on Canon 6D class cameras.</cons>
    </option>
    <option id="option-poll">
      <name>capture-preview poll loop (execFile every 150ms)</name>
      <pros>Simpler implementation — each invocation returns one complete JPEG (no SOI/EOI scanning). More predictable ~5-10 fps. No rolling buffer needed.</pros>
      <cons>Process-spawn overhead per frame (~30-100ms). Slightly more CPU. Does not use the camera's native push timing.</cons>
    </option>
  </options>
  <resume-signal>
    Select: option-movie OR option-poll
    (The executor will record your choice in the Wave 3 plan's action section and implement accordingly)
  </resume-signal>
</task>
